## Phase 5 — Secure code execution engine ✅ Complete (verified 2026-11-12)
- [x] Execution service (apps/execution) is real: internal-only API (`x-internal-token`, timing-safe compare, 401 otherwise; `/health` public), `POST /execute` (blocking, ≤30 s), `POST /execute/:executionId/cancel`, client-disconnect kills the job; job registry with concurrency cap (default 4 → 429 `EXECUTION_BUSY`). Validation: language allowlist (javascript/python/cpp), safe relative paths, ≤50 files, ≤1 MiB total, entry point ∈ files, ≤64 KiB stdin; stdout/stderr capped at 64 KiB with a truncation marker
- [x] Runner adapters behind one contract: **DockerRunner** (production default) — one `docker run` per step from the pure, unit-tested `buildDockerArgs()`: `--network none`, `--memory/--memory-swap 256m`, `--cpus 0.5`, `--pids-limit 64`, `--user 1000:1000`, `--cap-drop ALL`, `no-new-privileges`, `--read-only`, tmpfs /tmp 32m, `--ulimit core=0`, workspace as the only mount, fixed images (node:20-alpine / python:3.12-alpine / gcc:13-bookworm); unconditional cleanup (`docker kill`/`rm -f` + workspace delete); missing docker binary → honest FAILED, never a silent fallback. **SubprocessRunner** (dev/test only, NO isolation): process-group kill, RSS-polling memory enforcement; `EXECUTION_RUNNER=subprocess` + `NODE_ENV=production` crashes at boot
- [x] API: `ExecutionStatus` gained `CANCELLED` — real migration `20261112134943_phase5_execution_cancelled`. `POST /api/projects/:id/executions` (EDITOR+; language derived server-side from the entry extension; files resolved server-side — paths from File rows, content = live editor state or latest DocumentVersion), creator-only `GET /api/executions/:id` + `POST /api/executions/:id/cancel` (404 for everyone else, 409 when terminal), per-user rate limit 30/h + in-flight cap 2, client disconnect during a run = cancellation; service-down recorded as honest FAILED
- [x] Frontend: real Run/Cancel in the workspace header (elapsed timer while running), Output panel shows captured stdout/stderr + `Exit code · Duration · Status` footer and is labelled "not an interactive terminal"; Terminal panel keeps its honest not-connected label for interactive shells; VIEWER Run disabled ("View-only"); unsupported files surface the API 400 in the panel
- [x] Tests: execution 25 (Docker argv contract + env guards + real JS/Python/C++ runs, compile/runtime errors, timeout, memory hog, cancel, truncation, cleanup, via the subprocess runner), API 73 (+9 Phase 5: end-to-end runs in all 3 languages against real Postgres + the real service as a child process, role/ownership gates, 400, TIMEOUT, CANCELLED, service-down), web 67 (+10: store, Output panel, Run wiring, VIEWER gate). Live smoke: all three languages run through the public API; infinite loop → TIMEOUT; cancelled sleep → CANCELLED; no leftover workspaces. Full detail: `docs/execution.md`
- Limitations: **DockerRunner is implemented + unit-tested but NOT live-verified — this sandbox has no Docker daemon**; all live verification used the dev-only SubprocessRunner (no isolation). ## Phase 6 — Document persistence, autosave and version history ✅ Complete (verified 2026-11-13)
> **Renumbering note:** the earlier outline called Phase 6 "Hardening / Deploy" (and Phases 3–5 limitations below referenced it that way). Mourya's Phase 6 spec superseded it: Phase 6 is persistence/versions. Hardening/deploy (Redis scaling, Monaco self-hosting, Playwright E2E, Vercel/Render) becomes a **future phase pending Mourya's spec** — it is not numbered here.
- [x] Persistence hardening (collaboration): fetch/store retry with exponential backoff (250 ms → 2 s, `COLLAB_STORE_MAX_ATTEMPTS` default 4); a store that exhausts the budget is parked in an in-memory pending map (never dropped) and retried by a 5 s sweeper with the freshest live state; graceful shutdown force-stores every loaded document, bypassing the debounce; health endpoint exposes `pendingStores`. Residual risk stated in `docs/persistence.md`: a hard-killed collab process can lose up to one debounce window of edits held by no connected client
- [x] Persisted acknowledgements: stateless broadcasts `{type:"persisted", at}` after a store lands and `{type:"persist-failed"}` when a store is parked; the web save-status chip shows Saving… / Saved · HH:MM:SS / Save failed — retrying / Offline — changes stored locally, will sync (remote-origin updates never mark dirty)
- [x] Versions schema: `DocumentVersion.source` (`SAVE` | `SNAPSHOT` | `RESTORE` | `AUTOSAVE`, default `SAVE`) + optional `label` — real migration `20261113053148_phase6_version_source`; collab sync-back writes `AUTOSAVE`, explicit saves stay `SAVE`, labelled creates are `SNAPSHOT`. DTOs add source/label/author/sizeBytes; list never returns content, single GET does
- [x] Restore: `POST /api/files/:fileId/versions/:versionId/restore` (EDITOR+) snapshots the caller's live content first (`SNAPSHOT`, label "Before restore"), then applies the version **through the live document** via the collab server's token-guarded internal endpoint (`openDirectConnection` + CRDT transact, origin "restore") — no DB-only overwrite path exists; collab unreachable → 502 `COLLAB_UNAVAILABLE` with the document untouched (the pre-restore snapshot remains, documented). No separate restore row: the sync-back versions the restored state as AUTOSAVE
- [x] Frontend: Version History panel (list with timestamps/author/source badges/labels/sizes), Create-snapshot with optional label, Monaco DiffEditor modal (version vs current live content), restore behind an explicit confirmation that states the snapshot + live-replace semantics; VIEWERs get list + diff, no snapshot/restore. The editor content is never set locally on restore — it arrives via sync
- [x] Tests: collaboration 32 (+3 persistence units — retry-then-succeed, park-and-sweep with hook notifications, fetch retry; +4 integration — persisted ack broadcast, restore converging two live clients + AUTOSAVE sync-back + 401 without token, shutdown flush inside a 60 s debounce window, and a full DB stop/start outage: persist-failed → sweeper → persisted → fresh client receives full text), API 81 (+6 Phase 6: source/label/author/size metadata, restore happy path asserting the collab call + pre-restore snapshot, 502 path, VIEWER 403 / non-member 404, cross-file version 404, unknown version 404 writes nothing; +1 env unit), web 77 (+10: save-state machine incl. remote-origin and offline transitions, panel list/badges, diff props, restore confirmation + live-content payload, snapshot creation, VIEWER gates). Full detail: `docs/persistence.md`
- Limitations: pending stores live in the collab process's memory (a hard kill while parked relies on connected clients re-syncing — see the guarantees table in `docs/persistence.md`); version list is unpaginated (matches the Phase 2 list shape); restore requires the collab server to be running — by design, since a DB-only overwrite is forbidden.
